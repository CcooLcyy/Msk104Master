# CI 缓存治理

## 范围与目标

仅优化 Msk104Master 的 GitLab Windows CI，不修改上位机或其他工程的缓存。检查、测试和安装包构建统一使用 Windows x64 Release，关闭调试符号和增量编译，避免继续产生 Debug/Release 双份依赖及增量历史。

三个编译阶段同时启用 `custom-protocol` 特性，与 Tauri 安装包构建的生产配置一致，减少不同特性组合造成的重复产物。普通 Cargo 与开发模式的默认特性不变。

## 缓存边界与生命周期

- Cargo 缓存固定在当前工作区的 `target`，通过工作区及两个自有 crate 的清单确认身份；拒绝根目录、外部目录、符号链接和 Windows 重解析点。
- 迁移时仅清理经过身份及路径验证的本项目旧 `target/debug`；其他工程、Runner 公共 Cargo/npm 缓存、共享工具链不属于清理范围。
- 从 Cargo JSON 构建消息（包括 Fresh）记录三个阶段实际使用的自有及第三方 Cargo 产物、构建脚本输出和关联指纹。完整成功后，仅保留本轮检查、测试、打包所需的引用并回收确认不用的历史 Cargo 单元，不额外保留历史版本产物。
- 失败或取消时不推进成功历史；保护最近一次完整成功引用与本轮有效产物，便于重试。未知文件必须列入审计报告，不能猜测为冗余，也不能把未审计文件当成已经确认需要的缓存。
- Windows 作业使用项目级资源组串行执行，收尾由主脚本及 `after_script` 覆盖；硬中断后可在下一次准备阶段处理已登记的遗留失败记录。
- 取消收尾会重读本作业已写出的 Cargo JSON 日志。进程或主机硬中断、尚未输出或保存日志的产物无法精确归属，仍按未知产物保留，不能承诺这部分自动回收。

## 空间检查

准备、主要编译步骤之前和结束时记录本项目缓存体积及所在磁盘剩余空间。不设置缓存大小上限；文件是否保留由实际引用决定，不能因为总量较大删除仍在使用的依赖。最低可用空间检查默认 10 GiB，用于防止整个磁盘写满，不作为缓存淘汰依据。

仅保留变量 `MASTER_CARGO_MIN_FREE_GIB`（默认 `10`）。审计按目录和引用归属报告占用、确认冗余和无法确认的文件；项目独立 Rust 工具链、Runner 公共 Cargo/npm 下载缓存及其他工程分别说明，不能用单个工程的引用删除跨项目共享缓存。

## 验收

1. CI 中运行缓存边界测试，覆盖当前实际依赖保留、旧依赖与旧特性变体回收、Fresh 引用、连续失败保护、未知文件审计、路径逃逸和链接拒绝、旧 Debug 迁移及空间不足；大体积的有效缓存不能因已撤销的大小限制被拒绝或删除。
2. 最终提交通过前端构建、Rust 格式、Release Clippy、Release workspace 测试及 NSIS 打包；R2 发布方式保持原方案。
3. 日志与产物包含缓存回收和空间报告；失败时不能把流水线标记为成功。
4. 所有构建与测试均在 CI 执行；不在本地安装依赖、构建或运行测试。真实安装与跨版本更新仍需桌面人工验收。
5. 现有 Linux 发布作业在上传 R2 前再次执行 Python 边界测试，补足 Windows Runner 无权创建真实符号链接时的覆盖；任一用例失败都阻止发布。
