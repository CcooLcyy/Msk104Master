# CI 缓存治理

## 范围与目标

本规则适用于 Msk104Master 的 GitHub Actions Windows 作业。每次运行使用独立的托管 Runner，跨次仅缓存 npm 下载，不恢复 `target` 或独立 Rust 工具链。检查、测试和安装包构建统一使用 Windows x64 Release，关闭调试符号和增量编译，避免继续产生 Debug/Release 双份依赖及增量历史。

三个编译阶段同时启用 `custom-protocol` 特性，与 Tauri 安装包构建的生产配置一致，减少不同特性组合造成的重复产物。普通 Cargo 与开发模式的默认特性不变。

## 缓存边界与生命周期

- Cargo 缓存固定在当前工作区的 `target`，通过工作区及两个自有 crate 的清单确认身份；拒绝根目录、外部目录、符号链接和 Windows 重解析点。
- 准备阶段若发现本工作区的旧 `target/debug`，先验证身份和路径再清理。清理范围限于本项目的 `target`。
- 从 Cargo JSON 构建消息（包括 Fresh）记录三个阶段实际使用的自有及第三方 Cargo 产物、构建脚本输出和关联指纹。完整成功后保留本轮检查、测试、打包所需的引用，回收当前工作区中确认无引用的 Cargo 单元。
- 失败或取消时不写入新的成功记录。已有成功引用和本次已登记的产物继续受保护，直到工作区销毁或后续成功收尾。未知文件必须列入审计报告，不能猜测为冗余，也不能把未审计文件当成已经确认需要的缓存。
- 同一事件和 Git 引用的新 Windows 作业会取消旧作业。构建脚本处理正常收尾，工作流在失败或取消时另行重放已落盘的日志并登记结果。
- 进程或主机硬中断时，尚未记入日志的产物无法精确归属，仍按未知文件处理。
- Cargo 的构建锁、原始二进制及其配套信息属于必要缓存或控制元数据；旧脚本遗留的无对应产物 `.d`，须同时验证为本工程的 Cargo 依赖记录且当前无引用后才回收。
- 安装器复制到 `package/installer` 后，核对本作业来源及原件/副本摘要，清理重复的 bundle 安装器和明确生成的 NSIS 临时脚本；交付目录中的安装包、签名和其他未知文件不删除。

## 空间检查

准备、主要编译步骤之前和结束时记录本项目缓存体积及所在磁盘剩余空间。不设置缓存大小上限；文件是否保留由实际引用决定，不能因为总量较大删除仍在使用的依赖。最低可用空间检查默认 10 GiB，用于防止整个磁盘写满，不作为缓存淘汰依据。

工作流通过 `MASTER_CARGO_MIN_FREE_GIB` 设置最低剩余空间。审计按目录和引用归属报告项目 `target` 中的占用、确认冗余和未知文件。独立 Rust 工具链和 Cargo/npm 下载也占用磁盘空间，由整体剩余空间检查覆盖。

## 验收

1. CI 中运行缓存边界测试，覆盖当前实际依赖保留、旧依赖与旧特性变体回收、Fresh 引用、连续失败保护、未知文件审计、路径逃逸和链接拒绝、旧 Debug 迁移及空间不足；大体积的有效缓存不能因已撤销的大小限制被拒绝或删除。
2. 对应提交通过前端构建、Rust 格式、Release Clippy、Release workspace 测试及 NSIS 打包。R2 发布条件见 [GitHub Actions](GitHub-Actions.md)。
3. 日志与产物包含缓存回收和空间报告；失败时不能把流水线标记为成功。
4. 所有构建与测试均在 CI 执行；不在本地安装依赖、构建或运行测试。真实安装与跨版本更新仍需桌面人工验收。
5. Linux 发布作业在上传 R2 前再次执行 Python 边界测试，补足 Windows Runner 无权创建真实符号链接时的覆盖；任一用例失败都阻止发布。
